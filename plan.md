## Этап 1. «Что исследовать дальше» — сделано 18.10.2026

Как подсказки «Related» в Perplexity, только для длинных исследований. После отчёта DEEper предлагает следующие темы, и любую можно запустить в два клика.

- [x] **Предложения.** После сохранения отчёта один вызов Flash читает оглавление, выводы и пробелы и предлагает 5 тем трёх видов:
  - *углубить*: подтема, которую отчёт затронул вскользь;
  - *рядом*: смежная область;
  - *проверить*: где источники расходятся, риски, контраргументы, открытые вопросы.

  У каждой темы есть готовая формулировка запроса, строка «зачем» и рекомендуемый режим. Темы хранятся в JSON отчёта (`followups`), поэтому повторное открытие ничего не стоит. Для старых отчётов есть кнопка «Предложить темы».
- [x] **Приложение.** Под отчётом блок «Что исследовать дальше». Клик открывает форму нового исследования с заполненными темой, режимом и источниками. Запуск — второй кнопкой, чтобы случайный клик не тратил деньги.
- [x] **Уже в библиотеке.** Рядом показываем до 3 похожих прошлых отчётов (поиск FTS5, бесплатно), чтобы не исследовать заново то, что уже есть.
- [x] **Ветки исследований.** Новый отчёт хранит `parent`. На странице видно, продолжением какого отчёта он стал и какие отчёты продолжают его самого. Получается дерево исследований по теме.
- [x] **Бот.** Под итоговым сообщением кнопки с темами, затем выбор режима и запуск. Сами темы хранятся на сервере, а в кнопке только номер: Telegram ограничивает данные кнопки 64 байтами.
- [x] **Из вопросов.** Если ответ на вопрос по отчёту — «в отчёте этого нет», под ним появляется кнопка «Исследовать этот вопрос». `ask.py` уже просит модель подсказать, что исследовать отдельно.
- [x] **В файлах.** Раздел «Что исследовать дальше» в конце md, pdf и docx.
- [x] **Уточнение перед стартом** — кнопкой «Уточнить», как в deep research у ChatGPT: 2–3 вопроса с готовыми вариантами ответа (период, регион, для чего нужен отчёт), ответы встраиваются в тему. Цена ≈ 0,01–0,05 ₽.

Цена по замеру: 0,05 ₽ на подбор тем. Быстрый отчёт на Flash вместе с темами — 0,85 ₽.

## Этап 2.5. Разделение на части — сделано 19.10.2026

Цель: каждую часть можно улучшать и перезапускать отдельно, не задевая остальные. Решение от 18.10.2026: делаем после пункта 3.1 и сразу на четыре части, потому что модуль чтения из 3.1 уже обособлен и переедет в часть search. На Railway пока всё в одном контейнере и одном процессе, без доплаты. Перейти на отдельные сервисы Railway можно будет потом сменой настроек, без переписывания кода.

**Части**

| Часть | Что делает | Данные |
|---|---|---|
| **core** — ядро | веб-интерфейс, API для бота и исследователя, библиотека отчётов, очередь заданий, блок-лист, выдача файлов | единственная часть с доступом к volume `/app/reports` |
| **worker** — исследователь | исследование (GPT Researcher и наши доработки), подбор тем, уточнение темы, ответы на вопросы, сборка DOCX и PDF | своих данных нет: берёт задания у ядра и отдаёт ему готовые файлы |
| **bot** | Telegram-бот | своих данных нет, всё через API ядра |
| **search** — поиск | поиск и чтение источников (модуль `reader` из 3.1, отбор источников) | подключается к исследователю как свой поисковик GPT Researcher |

SearXNG остаётся как есть.

**Как части общаются**

API ядра:
- для интерфейса и бота:
  - создать задание и следить за ходом;
  - список отчётов и поиск по ним;
  - отчёт с вопросами и файлами, удаление, продолжения и похожие отчёты;
  - вопрос по отчёту, подбор тем, уточнение темы (ядро пересылает их исследователю);
  - блок-лист;
- для исследователя:
  - взять следующее задание;
  - отправить ход: этап, запросы, принятые источники с оценками, стоимость;
  - отдать файлы отчёта или ошибку.

У исследователя есть свой небольшой API: ответ на вопрос, подбор тем, уточнение темы.

Части проверяют общий токен, снаружи открыто только ядро, как сейчас. В режиме «один процесс» те же вызовы идут внутри процесса, без сети (httpx через ASGI). Контракт в обоих режимах один и тот же.

**Очередь заданий**
- Задания хранятся в SQLite ядра, а не в памяти: тема, режим, источники, писатель, родительский отчёт, откуда пришло (веб или бот), статус, этап, ход, стоимость, ошибка.
- Исследователь берёт задания по одному, как сейчас.
- Каждое сообщение о ходе служит «пульсом». Если пульса нет 5 минут, ядро помечает задание «прервано», а приложение и бот предлагают перезапустить его кнопкой. Это закрывает пункт этапа 5 «Очередь переживает перезапуск».

**Код**
```
my_browser/core/    интерфейс, API, библиотека, очередь, блок-лист   — группа зависимостей core (nicegui)
my_browser/worker/  движок исследования, подсказки, вопросы, экспорт  — worker (gpt-researcher, fastapi)
my_browser/search/  отбор источников и чтение страниц                 — search (gpt-researcher, fastapi)
my_browser/bot/     Telegram                                          — bot (aiogram)
my_browser/common/  настройки, клиенты API, токен, учёт стоимости
app.py              всё в одном процессе, как раньше: uv run app.py
eval/, research.py  работают с движком напрямую, без серверов
```
У каждой части свой `pyproject.toml` и свои зависимости (uv workspace). Заодно настройки запуска (источники, писатель) будут передаваться через отдельный конфиг на каждый запуск, а не через переменные окружения всего процесса. Тогда вопрос по отчёту во время исследования не подхватит чужую модель, а в будущем можно будет вести два исследования параллельно.

**Запуск**
- Локально всё вместе: `uv run app.py`, как сейчас.
- Локально по частям: своя команда для каждой части. Интерфейс и бот можно перезапускать, не прерывая исследование.
- Railway: один сервис и один процесс, как сейчас. Адрес и volume те же, к переменным добавится только токен.
- Позже — отдельные сервисы Railway: создать сервисы worker, bot и search, задать им команды запуска и внутренние адреса. Код не меняется, а цена вырастет на ≈ 170–245 ₽ в месяц за память.

**Шаги** (после каждого шага всё работает)
1. [x] API ядра поверх текущего кода и очередь в SQLite. Интерфейс переходит на те же функции.
2. [x] Исследователь отдельно: цикл «взять задание → исследовать → сообщать ход → отдать файлы» и API вопросов, тем и уточнения. Библиотека и файлы — только через ядро.
3. [x] Бот на API ядра.
4. [x] Режим «всё в одном процессе» и запуск по частям.
5. [x] Раскладка по пакетам и зависимостям, Dockerfile, `CLAUDE.md`, README.
6. [x] Проверка в обоих режимах:
   - исследование из приложения и бота;
   - продолжение отчёта, вопрос, уточнение, блок-лист;
   - перезапуск посреди исследования: задание становится «прервано», и его можно перезапустить.

   Один настоящий быстрый отчёт ≈ 1 ₽. Замер не нужен: движок исследования не меняется.
7. [x] Выкатка на Railway одним сервисом.

**Как сделано.** Проверено на поддельной модели в обоих режимах: исследование из приложения и бота, продолжение, вопрос, уточнение, блок-лист, обрыв процесса посреди исследования → «прервано» → «Перезапустить». Настоящий быстрый отчёт через новую схему: 0,78 ₽, 86 с. Отличия от плана:
- у частей не отдельные `pyproject.toml`, а группы зависимостей uv в одном: так проще, по умолчанию ставятся все;
- часть search пока отбирает источники и читает страницы, а сами поисковые движки по-прежнему вызывает GPT Researcher внутри исследователя — они переедут в search вместе с Exa (3.4).

**Что изменится для вас.** Тот же адрес, то же приложение и тот же бот. Новое: прерванные исследования видны, и их можно перезапустить кнопкой. Цена на Railway не меняется.

**Ограничение выбранного варианта.** На Railway любая правка по-прежнему пересобирает и перезапускает всё целиком. Сборка идёт около 6 минут, идущее исследование прервётся, но его можно будет перезапустить кнопкой. Это уйдёт при переходе на отдельные сервисы.

## Этап 5. Надёжность и обслуживание

- [x] **Очередь переживает перезапуск.** Задания хранятся в SQLite. После передеплоя прерванные задания видны в приложении и боте и перезапускаются одной кнопкой. Сделано в этапе 2.5.
- [ ] **Бот доводит задания после перезапуска.** Сейчас после перезапуска бот сообщает только о прерванных исследованиях. Если задание стояло в очереди, исследователь его выполнит, но отчёт в Telegram не придёт: он будет только в /history. При старте бот должен подхватывать активные задания из Telegram по `origin_ref`.
- [ ] **Отчёт не задваивается.** Если ядро приняло отчёт, а ответ не дошёл до исследователя, повторная отправка сохранит отчёт второй раз. Ядро должно узнавать повтор по номеру задания.
- [ ] **Проверка поиска перед стартом.** Если поиск запущен отдельным процессом (`SEARCH_URL`) и не отвечает, исследование не падает сразу, а пишет отчёт без источников. Нужно добавить поиск в предварительную проверку (`preflight`).

## Что ещё изучить: идеи из других проектов

- **[DeepResearch Bench](https://github.com/Ayanami0730/deep_research_bench)** (ICLR 2026): 100 задач уровня PhD из 22 областей и две методики оценки.
  - RACE оценивает полноту, глубину, следование заданию и читаемость. Возьмём её, чтобы сравнивать Flash и Pro не на глаз.
  - FACT проверяет ссылки: извлекает пары «утверждение → URL» и смотрит, подтверждает ли страница утверждение. Возьмём её для метрики точности цитирования (этап 2).
- **[STORM](https://github.com/stanford-oval/storm)** (Стэнфорд): план статьи строится из смоделированных разговоров автора, у которого есть определённая точка зрения, с экспертом, который опирается на источники. Для подробного режима: генерировать подтемы от лица 3–4 ролей (инженер, экономист, регулятор, скептик). Охват будет полнее, а стоит это один вызов Flash.
- **[open_deep_research](https://github.com/langchain-ai/open_deep_research)** (LangChain): руководитель раздаёт подзадачи параллельным исследователям, и каждый сжимает свои находки до написания. Отсюда добор пробелов (3.9) и сжатые конспекты по подтемам, чтобы писатель читал меньше токенов.
- **[node-DeepResearch](https://github.com/jina-ai/node-DeepResearch)** (Jina): цикл «поиск → чтение → рассуждение» идёт, пока не найден ответ или не кончился бюджет токенов. Идея для нас — бюджет в рублях: «исследуй на 5 ₽» вместо фиксированной глубины.
- **[Local Deep Research](https://github.com/LearningCircuit/local-deep-research)**: полностью локальный режим и разные стратегии поиска. Запасной вариант за 0 ₽ и материал для сравнения стратегий.

| **Итого** | **≈ 210–240 из 300** |

В пиковые часы DeepSeek стоит вдвое дороже: подробный на Pro тогда ≈ 24 ₽, поэтому его лучше запускать вне пика (этап 4). Railway оплачивается отдельно, как сейчас. Запросов к поисковикам по грубой оценке выйдет 400–500 в месяц: это в пределах бесплатных лимитов и Tavily (1 000 запросов), и Exa ($10). Точные цифры даст учёт из пункта 3.7.
